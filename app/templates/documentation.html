Browsing & viewing

GET/{path}

The catch-all route behind the whole browsing UI on cdn.amit.is-a.dev. What it renders depends on what path resolves to:

If path is...Renders
empty (/)Root folder listing, plus the homepage hero/notice.
an existing fileA file detail page (preview where possible, size, copy-link/copy-raw buttons, download).
an existing folderA folder listing (files and sub-folders, with search-this-folder and "Download all" zip).
nonexistent404 page.

How it decides

It calls get_file_info(path) first (a HEAD request against the Hugging Face bucket's resolve URL for that path). If that says the path exists as a file, it renders the file page. Otherwise it calls list_directory(path) (a tree listing from the HF bucket API); a non-empty result renders the folder listing, an empty result on a non-root path is a 404.

Errors

  • 404 Path doesn't exist as a file or a non-empty folder.
GET/new GET/find

/new renders the upload UI (drag-and-drop → calls /api/put under the hood). /find renders the search UI (calls /api/find as you type). Both are just the same index.html template rendered with a different page context value — no separate backend logic beyond that.

GitHub Actions sync

GET/gh-sync

Renders the human-readable setup guide for the feature below, including a copy-pasteable workflow file. No parameters, no backend logic beyond rendering the template.

POST/api/gh-sync

Lets a GitHub Actions workflow push a repo's files to the CDN on every push, landing at /<github-username>/<repo-name>/ — with no PAT or shared secret required. Full setup instructions (including the exact workflow YAML to copy) are at /gh-sync.

Request

multipart/form-data with two fields:

FieldWhat it is
tokenA GitHub Actions OIDC identity token, requested by the calling workflow via core.getIDToken('cdn.amit.is-a.dev'). This is the only source of identity this endpoint trusts.
archiveA .tar.gz of the repo's contents (the workflow builds this with tar --exclude='.git' -czf ...).

How it works, step by step

  1. Verifies the token's signature against GitHub's own public keys (token.actions.githubusercontent.com/.well-known/jwks), checks it isn't expired, and checks the aud claim matches this service.
  2. Reads repository_owner, repository and the numeric repository_owner_id straight out of the verified token claims — this is the destination folder and the identity of the sender, and it is never taken from anything else in the request. A workflow file cannot forge these claims because GitHub itself stamps them for the run.
  3. Refuses banned visitors and banned GitHub accounts, then applies the approval rule: the first sync from a GitHub account is accepted automatically; after that, the account must have been approved by the CDN owner or the sync is refused with 403. Accounts are tracked by GitHub's numeric owner ID, so renaming an account or re-registering an old username does not bypass this. The CDN owner's own account is always allowed.
  4. Rejects the archive with 413 if the compressed .tar.gz is larger than 200 MB, before reading any of it into memory.
  5. Extracts the tar archive into a temp directory, rejecting anything that tries to write outside that directory (path traversal) or that is a symlink.
  6. Rejects the whole sync if any file is a video, detected by extension and by file signature (so renaming a video does not help). Nothing is uploaded in that case.
  7. Uploads that folder to the Hugging Face storage bucket with the destination and the delete scope both limited to exactly <owner>/<repo>/ — so the call can create, update, or delete files only inside that one folder, never anywhere else. Files deleted from the source repo are removed from the CDN folder too (this is a mirror, not an accumulate-forever upload). The bucket keeps no version history, so those removals are permanent.

Response 200

{
  "synced_to": "jaasx009/College",
  "cdn_url": "https://cdn.amit.is-a.dev/jaasx009/College/",
  "raw_url_prefix": "https://raw.cdn.amit.is-a.dev/jaasx009/College/",
  "note": "cdn_url is the browsable folder listing. raw_url_prefix isn't a link by itself - append an individual filename to it to get that file's direct raw URL.",
  "ref": "refs/heads/main"
}

Errors

  • 401 Token missing, expired, badly signed, wrong audience, or its owner/repository claims don't line up (malformed token).
  • 400 Archive isn't a readable .tar.gz, or it contains an unsafe path / a symlink.
  • 403 The sender's IP or GitHub account is banned, or this account's first sync was already accepted and further syncs need approval from the CDN owner. The message says which.
  • 413 The compressed archive is larger than 200 MB. Nothing is synced.
  • 415 The archive contains a video file. The message names the file and nothing is synced.

Limits, currently

Any file type except video, and no limit on the number of files. GitHub sync has no rate limit, but the compressed .tar.gz can be at most 200 MB. What protects it instead is the sign-in identity, the approval rule, bans and the video rule above. See Rate limits.

Uploading files

POST/api/put

Direct multipart file upload — what the /new page's drag-and-drop calls. For uploading from a GitHub repo automatically, use /api/gh-sync instead; this endpoint is for one-off manual uploads.

Request

FieldWhat it is
filesOne or more files (multipart, repeatable field).
folderOptional. Must be exactly uploads or third-party — these are the only two folders this endpoint is allowed to write to. Defaults to uploads.

How it works

Each file is streamed to a temporary file named only by a random ID (your filename is never used in a filesystem path), then checked in this order: banned IP, VPN/proxy address, video (by extension or file signature), and the upload limit (200 MB per hour per client IP). It is then stored in the bucket at <folder>/<8-char-uuid>-<filename>. Any filename is accepted: directory parts are dropped, accents are simplified, and anything other than letters, digits, ., _ and - becomes an underscore (my file (1).png is stored as ab12cd34-my_file_1.png). The random prefix means two uploads can never collide, and the filename portion is still readable. If 2 or more files were uploaded together, a batch is also created (see Batches below) so the whole set can be shared/downloaded as one link.

Response 200

{
  "files": [
    {"filename": "photo.png", "hf_path": "uploads/ab12cd34-photo.png",
     "size": 48213, "cdn_url": "...", "raw_url": "..."}
  ],
  "batch_id": "a1b2c3d4e5",     // only present if 2+ files
  "batch_url": "https://cdn.amit.is-a.dev/pack/a1b2c3d4e5"
}

Errors

  • 400 folder isn't uploads or third-party.
  • 403 Your IP is banned, or the upload comes from a VPN/proxy address.
  • 415 The file is a video (.mp4, .mov, .webm, .mkv and similar, or recognised by its contents). Videos are not accepted on this CDN.
  • 413 A single file is larger than 200 MB (waiting won't help; split it).
  • 429 You have used your 200 MB for the hour. See Rate limits.
POST/api/put-url

Uploads a file the server fetches from a URL you give it, instead of one you send directly. Same destination rules and checks (ban, VPN/proxy, video) as /api/put, but with its own smaller allowance: 50 MB per hour per IP, separate from your file-upload allowance. The file name is taken from the URL or the response's Content-Disposition and sanitised the same way.

Request

JSON body:

{ "url": "https://example.com/file.png", "folder": "uploads" }

How it works / safety

Only https:// URLs are accepted. Before fetching, the hostname is resolved and every returned IP is checked — private, loopback, link-local, reserved, multicast, or unspecified addresses are all rejected. This is an SSRF guard: without it, this endpoint could otherwise be used to make the server fetch internal/local network addresses on the caller's behalf. The download is streamed with a size cap enforced both from the Content-Length header (if present) and live as bytes come in, so a server lying about its own content-length can't bypass the cap.

Response 200

Same single-file shape as one file from /api/put's response (no batch, since it's always exactly one file).

Errors

  • 400 Not https://, hostname doesn't resolve, resolves to a private/internal address, or the source returned a non-200.
  • 403 Your IP is banned, or the request comes from a VPN/proxy address.
  • 413 The file is larger than 50 MB, the most that can be fetched from a link. The download is stopped as soon as it passes the limit.
  • 415 The downloaded file is a video.
  • 429 You have used your 50 MB for the hour for uploads from a link. See Rate limits.

URL shortener

GET/shorten

The page for creating short links. It calls the API below.

POST/api/shorten

Turns a long https:// URL into a short /mask/<id> link on this domain.

Request

{ "url": "https://example.com/some/long/page" }

How it works / safety

Only https:// URLs of at most 2048 characters are accepted. The hostname is resolved and every address is checked — private, loopback, link-local and other internal addresses are rejected, the same SSRF guard used by /api/put-url. Each client IP is limited to 10 requests per minute and 50 per hour; the limit is counted before the hostname lookup, so rejected attempts count too. The destination is stored as a small object in the bucket under a random 8-character ID.

Response 200

{
  "id": "abc123XY",
  "masked_url": "https://cdn.amit.is-a.dev/mask/abc123XY"
}

Errors

  • 400 Not https://, longer than 2048 characters, invalid, host doesn't resolve, or it points to a private/internal address.
  • 403 Your IP is banned.
  • 429 More than 10 requests in a minute or 50 in an hour from your IP. See Rate limits.
GET/mask/{short_id}

Redirects to the stored destination with a 307 and a Referrer-Policy: no-referrer header, so the destination site doesn't see which page the visitor came from.

Errors

  • 404 No short link with that ID.

Rate limits

Limits keep the storage free for everyone and stop one visitor from filling it. They apply only to things that write: uploading files, uploading from a link, and shortening a link. Browsing, search, viewing, downloads, zips and GitHub sync are not rate-limited by this app.

At a glance

WhatLimit
/api/put200 MB per hour, counted in bytes, per IP. No per-minute limit. A single file can be at most 200 MB.
/api/put-url50 MB per hour, counted in bytes, per IP. This is a separate allowance from file uploads. A single file can be at most 50 MB.
/api/shorten10 per minute and 50 per hour, counted in requests, per IP.
/api/gh-syncNo rate limit. The compressed archive can be at most 200 MB.

How the limits work

  • Sliding window. Your usage is totalled over the last 60 minutes (the shortener also looks at the last 60 seconds). There is no clock-time reset: old uploads age out one by one, so your allowance returns gradually.
  • Per IP. The limit follows the address your request really comes from. People on the same network (office, school, mobile carrier) share one allowance. Uploads from VPN or proxy addresses are refused outright, whatever your usage.
  • Bytes, not files. Ten 1 MB files use the same allowance as one 10 MB file. Each file is checked when it arrives.
  • Two separate allowances. Uploading from a link never uses up your 200 MB of file uploads, and file uploads never use up your 50 MB for links.
  • Biggest single file. 200 MB for file uploads and 50 MB from a link. A file over that is refused with 413 rather than 429, because waiting would not help. From a link, the download stops as soon as it passes 50 MB.
  • Batches stop at the limit. If you upload several files in one request and the limit is reached partway, the request fails with 429. Files already stored earlier in that request stay stored.
  • What does not count. Uploads refused before the limit check (banned IP, VPN/proxy address, video) do not use your allowance. Shortener requests do count even when the URL turns out to be invalid, because the limit is checked before the link is examined.
  • GitHub sync is not rate-limited, but the compressed archive can be at most 200 MB. It is protected by the sign-in identity, the approval rule, bans and the video rule (see GitHub Actions sync).
  • In memory. Counters are kept in the server's memory, so a restart or redeploy clears them.

When you hit a limit

The response is 429 (or 413 for a file that is too big) with a JSON message. There is no Retry-After header, so use the message to see which limit you hit:

{ "detail": "Upload rate limit exceeded: 200.00 MB/hour. Try again later." }
{ "detail": "URL upload rate limit exceeded: 50.00 MB/hour. Try again later." }
{ "detail": "Rate limit exceeded: 10 requests/minute. Try again shortly." }
{ "detail": "Rate limit exceeded: 50 requests/hour. Try again later." }
{ "detail": "File too large (limit 200.00 MB per file)." }
{ "detail": "Archive too large (limit 200.00 MB after compression)." }

After a minute message, wait up to a minute. After an hour message, wait until earlier uploads are an hour old. For file too large, waiting doesn't help: make the file smaller or split it.

Staying under the limits

  • Upload big batches in smaller groups, and leave time between them if you are close to 200 MB in an hour.
  • Compress or resize large files before uploading.
  • Have a whole project to move? GitHub sync has no rate limit.

Downloading & zips

GET/api/get/{path}

Forces a browser download of a single file (sends Content-Disposition: attachment), unlike viewing the raw domain which lets the browser render the file inline if it can. Streams the file through this server rather than redirecting to Hugging Face directly, and supports Range requests (so video/audio seeking and resumable downloads work).

Errors

  • 404 File doesn't exist.
GET/api/pack-info/{path} GET/api/pack/{path}

pack-info returns the file count and total size a folder would zip to, without actually building the zip — used by the UI to show a size estimate before you commit to downloading. pack builds and streams the actual zip.

How it works

Lists every file under path recursively via the HF API, fetches up to 8 of them concurrently, and streams them into a zip in memory (paths inside the zip are relative to the folder you asked for, not absolute). There's a hard limit of 300 files / 200 MB total per zip — past that it refuses rather than trying to build an enormous zip in memory.

Errors

  • 404 Folder is empty or doesn't exist.
  • 413 Folder exceeds the 300-file / 200 MB zip limit.

Multi-file batches

When /api/put is given 2 or more files in one request, it also writes a small "batch manifest" (just the list of resulting files) under a random 10-character batch ID, so that whole set can be shared and managed as a single link instead of separate ones.

GET/pack/{batch_id}

Renders a page listing every file in that batch, with per-file and "download all as zip" options.

Errors

  • 404 No batch with that ID.
GET/api/pack-info-batch/{batch_id} GET/api/pack-batch/{batch_id}

Same idea as /api/pack-info / /api/pack above, but operating over the batch's file list instead of a folder path. No 300-file/500MB check here since a batch is inherently one upload's worth of files, not an arbitrary folder walk.

Errors

  • 404 Batch doesn't exist, or exists but is empty.

Search

GET/api/find?q=...

Powers the /find page. Takes a query string q, returns matching files across the whole repo.

Response 200

Stats

GET/stats

A page of charts about what is on the CDN: file types (by count or by size), the most common extensions, a file-size histogram, the biggest folders, files added per month, and the largest files. It loads its data from /api/stats and draws everything with plain CSS and inline SVG, so the page stays tiny.

GET/api/stats

The JSON behind the page. It contains aggregate numbers only — no IP addresses and no upload history. It is computed from the same cached file listing used for browsing and search and recomputed at most every 10 minutes, so calling it never adds load on the bucket. The response is sent with Cache-Control: public, max-age=300.

The raw domain

GET/{path} raw.cdn.amit.is-a.dev

A separate hostname, not a path prefix on the main domain. Requests here are proxied straight through to the underlying file in the Hugging Face bucket (its resolve URL), with no HTML wrapper — this is meant for direct file links (<img src>, downloads, embeds), not browsing.

If the path is a folder, not a file

The direct file fetch 404s (Hugging Face's resolve only serves blobs). Before giving up, this checks whether that path is actually a non-empty folder — if so, it 307-redirects to the equivalent listing page on the main domain (cdn.amit.is-a.dev/<path>/) instead of just saying not-found. A genuinely nonexistent path still 404s.

Errors

  • 404 Path doesn't exist as a file or a non-empty folder. Response body is plain text, not the HTML 404 page (deliberately - this is meant to be machine/embed-friendly, not a browsing experience).
GET/raw/{path} cdn.amit.is-a.dev

A convenience prefix on the main domain that just 307-redirects to the real raw domain — i.e. cdn.amit.is-a.dev/raw/foo.png → raw.cdn.amit.is-a.dev/foo.png. Not itself a proxy.

How storage actually works

Everything above talks about "the CDN" as one thing, but there's no custom database or file server behind it — every file this service serves, lists, or accepts lives in a single Hugging Face Storage Bucket. A bucket is plain object storage, not a git repository, so there is no commit history that grows as files pile up. This app is a FastAPI backend in front of that bucket:

  • File listings (folders, search, file-exists checks, stats) come from the bucket's tree API, with a short-lived in-memory cache on this server's side so repeated browsing doesn't re-hit that API constantly.
  • Serving an actual file's bytes (viewing, raw links, downloads, zips) streams from the bucket's public resolve URL — this server proxies that stream rather than storing a separate copy.
  • Uploads (/api/put, /api/put-url, /api/gh-sync) all ultimately call the Hugging Face bucket API to write objects into that same bucket, each scoped to whatever folder/path rules that endpoint enforces.
  • There is one HF write token, held only by this server - never handed to uploaders, contributors, or GitHub Actions runs. Everything that writes to storage goes through this backend's own validation first (folder allow-lists, OIDC identity checks, bans, rate limits) precisely because the write credential itself has no per-user restriction built in - the backend is the access control.
  • No version history. Overwritten or deleted files can't be restored from history, and a GitHub sync that removes files from a folder removes them for good.
  • A few internal folders live in the same bucket (batch records, short links and the site's own moderation data). They are hidden from listings and search, and the moderation data is encrypted.
